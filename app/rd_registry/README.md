# rd_registry: реестр «наших РД»

Операторы CRM карточек товаров часто вводят один и тот же наш РД (номер, тип, даты). Модуль запоминает эти РД,
и оператор выбирает нужный в модалке «Реестр РД» на странице CRM-редактирования карточки. Реестр ведут на странице
администрирования `/rd_registry/`, ссылка «Реестр РД» есть в меню CRM.

## Состав

- `normalize.py`: `rd_key()` строит ключ поиска номера: верхний регистр, кириллические двойники -> латиница,
  без пробелов и пунктуации. Копия алгоритма лежит в `rdKey()` в `static/rd_registry/rd_picker.js`, менять их вместе.
- `models.py`: `RdRegistryEntry`, таблица `rd_registry`. Уникальный ключ `(search_key, rd_date, rd_date_to, category,
  subcategory, tnved_code)`: номер с другими датами, в другой категории или с другим ТНВЭД хранится отдельной записью,
  а кириллическое и латинское написание одного номера не дублируются.
  - `category` = `ProductCard.category`.
  - `subcategory` = подкатегория позиции, если она есть у категории в `CATEGORIES_COMMON`
    (`views/main/product_cards/support.py`), иначе `''`.
  - `tnved_code` = ТНВЭД позиции карточки, `''`, если в карточке его нет.
  - `is_archived` заменяет удаление.
  - `created_by`/`created_at`: кто и когда добавил. `updated_by`/`updated_at`: кто и когда последним правил запись
    вручную (правка, архив, возврат).
- `service.py`:
  - `remember_rd()`: upsert в текущую сессию без commit.
  - `search_rd()`: подсказки для модалки.
  - `list_rd()`, `save_rd()`, `set_archived()`: страница администрирования, тоже без commit (коммитят роуты).
  - `category_choices()`: категории карточек без отключённых (`PC_DISABLED_CARD_CATEGORIES`).
  - `category_label()`: подпись вида «одежда / шали» или «парфюм».
- `routes.py`: blueprint `rd_registry`. `GET /search` отдаёт подсказки CRM-ролям (`bck_sumausmumu_required`).
  `GET /`, `POST /save` и `POST /<id>/archive` обслуживают страницу администрирования. Blueprint добавлен
  в `allowed_blueprints` в `settings/handlers.py`, без этого `manager_forbidden_handler` редиректит операторов.
  В nginx отдельного правила не нужно: `location /` в `nginx/nginx.conf` отдаёт во Flask все пути.
- `templates/rd_registry/picker_modal.html` и `static/rd_registry/rd_picker.js`: модалка подсказок.
- `templates/rd_registry/index.html`: страница администрирования. Наследует `main/base_v2.html` (блок `fc_panel`),
  как остальные админ-страницы, поэтому у неё общий сайдбар, меню пользователя и toast-уведомления.
- `templates/rd_registry/_results.html`: вкладки, фильтры, таблица и пагинация. `index.html` включает его, а на запрос
  с `X-Requested-With: XMLHttpRequest` роут `GET /` отдаёт только его.

## Когда пополняется

1. `h_update_product_card(crm_=True)` в `views/main/product_cards/handlers.py`, если оператор сохранил карточку
   с изменённым блоком РД. Категорию берём у карточки, подкатегорию и ТНВЭД у её позиции (`subcategory` и `tnved_code`
   модели категории; `common` у носков отбрасывается). Если такой РД в той же категории уже есть, растут `usage_count`
   и `last_used_at`. Из архива запись при этом не возвращается.
2. Ручное добавление на странице администрирования, с `usage_count = 0`.

Создание карточки и правки клиента в реестр не пишутся. Таблица стартовала пустой, историю не переносили.

## Поиск

`GET /rd_registry/search?q=&tnved=`, где `tnved` это ТНВЭД карточки (поле `#tnved_code` на странице).

- `q` пустой или короче 5 символов, `tnved` есть: предзагрузка РД с этим ТНВЭД. Нет ни того, ни другого: пустой ответ.
- `q` нормализуется через `rd_key()`. С 5 символов ищем номер по всему реестру, РД с ТНВЭД карточки идут первыми.
- Совпадение ищется по вхождению (`search_key LIKE '%q%'`): начало у номеров одинаковое («ЕАЭС N RU Д-…»),
  а различаются они серийным номером в конце, например `23280/26`.
- В выдачу попадают только неархивные РД с `rd_date_to >= сегодня + 1 месяц` (`min_suggest_date()`). Это то же правило,
  что в `validate_rd_block`: с более коротким сроком карточку не сохранить.
- Фильтров по категории нет, категория и ТНВЭД показаны оператору колонками.
- Порядок: сначала РД с ТНВЭД карточки, дальше `usage_count desc, last_used_at desc`. Отдаём не больше 20 записей
  и флаг `has_more`, у каждой записи есть `days_left`.

Ответ:

```json
{"status": "success", "has_more": false,
 "items": [{"id": 1, "rd_type": "Декларация соответствия", "rd_name": "ЕАЭС N RU Д-CN.РА02.В.23280/26",
            "rd_date": "25.09.2026", "rd_date_to": "23.04.2027", "days_left": 200,
            "category": "одежда / шали", "tnved_code": "6214100000", "search_key": "EAЭCNRUДCNPA02B2328026"}]}
```

## Фронт (rd_picker.js)

- Кнопка «Реестр РД» стоит в одной строке с заголовком блока РД (`product_cards/new/categories/helpers/rd.html`)
  и выводится только при `crm_`. Блок виден, когда тумблер РД включён. Модалка размера `modal-xl`.
- При открытии модалки берём ТНВЭД из `#tnved_code` и подгружаем РД с ним, один запрос на открытие.
- Ввод обрабатывается после паузы 250 мс. Пока ключ короче 5 символов, запросов нет: подгруженный список фильтруется
  по введённому.
- Если на ключ K сервер ничего не нашёл, запросы не отправляются, пока ключ содержит K.
- Если на ключ K пришло `has_more=false`, дальнейшее уточнение фильтрует полученный список без запросов.
- При `has_more=true` каждое уточнение уходит на сервер. Устаревший запрос отменяется через `AbortController`.
- Клик по строке включает тумблер РД, заполняет `rd_type` (select2), `rd_name`, `rd_date` и `rd_date_to`, нормализует
  даты через `window.pcNormalizeRdDates()` и закрывает модалку. Сохраняет карточку оператор обычной кнопкой.
- «Применить» активна, когда поле ввода не пустое. Она нужна, если РД в реестре нет: включает тумблер и подставляет
  введённый текст без `№` в `rd_name`, тип и даты оператор заполняет сам. В реестр такой РД попадёт после сохранения
  карточки.

## Страница администрирования `/rd_registry/`

- Доступ задают константы в `routes.py`. `ACCESS_ROLES = {superuser, supermanager}`: страница, добавление и правка.
  `ARCHIVE_ROLES = {superuser}`: архив и возврат. Операторы (`manager`) пользуются только поиском из карточки,
  остальные получают 403.
- В хлебных крошках у superuser ссылка «Панель администратора», у supermanager «CRM карточки товаров». Ссылку
  «Реестр РД» в меню CRM (`product_cards/crm/helpers/user_tab.html`, `crm_mod_v1/helpers/user_tab.html`) видят те же
  `ACCESS_ROLES` через глобал шаблонов `rd_registry_access_roles`.
- На странице есть вкладки «Активные» и «Архив», фильтры по категории и типу РД, флажок «Скрыть истёкшие», по 50 записей
  на страницу. Поиск идёт по номеру с той же нормализацией, но без порога в 5 символов. Если введены только цифры,
  они ищутся ещё и как начало ТНВЭД (`6214` найдёт шали). В таблице есть колонки «Категория» (`category_label()`)
  и «ТНВЭД».
- Таблица помещается без горизонтального скролла на экранах от ~1280px: `container-fluid`, шрифт `small`, «От» и «До»
  в одной колонке «Действует», кнопки действий столбиком. Контент в `base_v2` это flex-элемент с `min-width: auto`,
  и слишком широкая таблица растягивает всю страницу вместе с шапкой. Новые колонки добавлять с оглядкой на ширину.
- Сортировка переключается стрелками в заголовках «Добавил» (`created_at`) и «Изменил» (`updated_at`, записи без правок
  всегда в конце): `?sort=created|updated&dir=asc|desc`, по умолчанию `created desc`. Фильтры и сортировка сохраняются
  во всех ссылках страницы.
- Подсветка: истёкшие РД красные, РД с «До» меньше чем через месяц жёлтые (их нет в подсказках).
- Добавление и правка идут через одну модалку с `<input type="date">`.
  - Категория обязательна. Поле «Подкатегория» появляется, только если у категории есть подкатегории, и заполнять его
    не обязательно.
  - ТНВЭД обязателен, 10 цифр.
  - Остальные правила как у блока РД карточки: тип из `settings.RD_TYPES`, номер от 3 до 100 символов без `№`, «От»
    с 01.01.2022 по сегодня. Отличие одно: «До» должна быть не раньше «От», без условия «+1 месяц», чтобы можно было
    поправить старую запись.
  - Дубль `(search_key, даты, категория, подкатегория, ТНВЭД)` отклоняется, даже если он лежит в архиве.
- Правка записи не меняет РД в карточках: у карточки своя копия полей РД.
- Удаления нет, есть «В архив» и «Вернуть». Архивные РД в подсказках не показываются.
- Сортировка, вкладки, пагинация, поиск и фильтры не перезагружают страницу: JS в `index.html` запрашивает тот же URL
  с `X-Requested-With`, подменяет `#rdResults` ответом и обновляет адрес через `history.pushState` (ссылка и «Назад»
  работают). Категория, тип и «Скрыть истёкшие» применяются сразу, поиск по Enter или «Найти». Если сессия истекла
  или запрос упал, JS уходит обычным переходом.
- Сохранение и архив отправляются обычным POST и перезагружают страницу. После действия она открывается с теми же
  фильтрами через `next`, принимаются только пути `/rd_registry/...`.

## РД оператора и клиент

Блокировки нет. Клиент на статусе «На уточнении» может изменить или снять любой РД карточки, в том числе введённый
оператором.

## Чего нет

- Удаления записей (есть только архив) и массового импорта, например из таблицы РД по странам.
- Привязки РД к стране и компании обработки.
- Фильтров в модалке карточки, они есть только на странице реестра.
- Индекса под поиск по номеру. Для тысяч строк хватает полного прохода, при 100k+ нужен GIN `pg_trgm` по `search_key`.
