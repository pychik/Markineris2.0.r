# Toys Category Context

Рабочий контекст для будущего модуля категории `toys`.

## Текущий статус

- Папка `app/views/main/categories/toys/` заведена как рабочая зона для новой категории игрушек.
- Сейчас внутри лежат Excel-таблицы распределения подкатегорий и ТН ВЭД.
- Файлы справочников переименованы в человекочитаемый вид без технических префиксов `IMPORT_K3`, `IMPORT_TNVED` и ведущих `__`.
- Category-flow для `toys` заведён первым вертикальным срезом.
- Рабочие подкатегории:
  - `doll_accessories` — `Аксессуары и принадлежности для кукол`;
  - `puzzles` — `Головоломки`;
  - `competition_cars` — `Гоночные автомобили для соревновательных игр`;
  - `sets_kits` — `Игрушки в наборах, комплектах`;
  - `motorized_toys` — `Игрушки и модели со встроенным двигателем`;
  - `animal_creature` — `Игрушки, изображающие животных или других существ`.
- Добавлена модель `Toys`, связь с `Order`/`ProductCard` и миграции таблицы `toys`.
- Для toys-подкатегорий с полем `Тип привода в движение` в `Toys` добавлено поле `drive_type` через миграцию `8e2f9a7c1d4b_add_drive_type_to_toys.py`.
- Blueprint `toys` зарегистрирован на `/toys`.
- На странице входа отдельная плитка `Игрушки` стоит рядом с `Косметика`, помечена badge `New` и ведёт на промежуточную страницу подкатегорий.
- Старая плитка `Товары для дома и игрушки (ТГ)` оставлена отдельной плиткой со ссылкой на Telegram.
- Активные заказы в книжке заказов пользователя учитывают `toys` как категорию с подкатегориями.
- Summary и общие шаблоны подтягивают названия toys-подкатегорий через общий словарь `SUB_CATEGORIES_DICT`.

## Планируемый подход

Категорию `toys` развивать по аналогии с `cosmetics`:

- отдельный blueprint категории;
- path-based route-ы вида `/toys/<subcategory>/...`;
- отдельная стартовая страница выбора подкатегории;
- enum подкатегорий;
- registry subcategory-config;
- данные и отличия подкатегорий держать в config-модулях, а не размазывать отдельные `if` по views, JS и export;
- общий helper рендера категории;
- переиспользуемые шаблоны шага 2 и шага 3 там, где подкатегории имеют одинаковую форму;
- отдельный README вести как рабочий лог по мере добавления подкатегорий.

## Рабочий flow

### `doll_accessories`

- Название: `Аксессуары и принадлежности для кукол`.
- Источник справочника заменён из файла:
  `/home/chik/Downloads/Telegram Desktop/Аксессуары_и_принадлежности_для_кукол.xlsx`.
- Локальная рабочая копия:
  `app/views/main/categories/toys/Аксессуары и принадлежности для кукол.xlsx`.
- Лист шаблона: `IMPORT_CATEGORY_237033`.
- Лист справочников: `Справочники`.
- Код категории проставляется автоматически по выбранному ТН ВЭД:
  - `9503002900` -> `237033`;
  - `9503001001` -> `551734`.
- В правой итоговой плашке статически показывается список возможных кодов `237033 / 551734`; визуально он не меняется при выборе ТН ВЭД.
- Из правой итоговой плашки убрана строка `Сумма по накладной / Не указано`; JS-обработчиков суммы для toys не осталось.
- Разрешённые ТН ВЭД:
  - `9503002900` — аксессуары и принадлежности для кукол;
  - `9503001001` — коляски для кукол.
- Текущая форма совместима со справочником `Коляски для кукол.xlsx`: внутри той же подкатегории добавлены виды товара `КОЛЯСКА ДЛЯ КУКОЛ` и `КОЛЯСКА-ТРОСТЬ ДЛЯ КУКОЛ`.
- `Вид товара` ограничивает только доступный список ТН ВЭД:
  - аксессуары, одежда, обувь и головные уборы для кукол -> только `9503002900`;
  - коляски и коляски-трости для кукол -> только `9503001001`;
  - `НЕТ В СПРАВОЧНИКЕ` -> оба ТН ВЭД, потому что значение есть в обоих справочниках.
- ОКПД2 берётся из `Маппинг ТН ВЭД и ОКПД2.xlsx` по ТН ВЭД:
  - `32.40.13.111` — одежда и принадлежности, обувь и головные уборы для кукол;
  - `32.40.13.119` — аксессуары для кукол прочие.
  - `32.40.31.110` — коляски для кукол.
- В Excel-маппинге нет связи с `Вид товара`; ОКПД2 мапится только по выбранному ТН ВЭД.
- ОКПД2 выбирается через модальное окно по паттерну ТН ВЭД: пользователь видит код и описание, в поле формы записывается только код.
- В предпросмотре и карточке позиции отображается только `Код ОКПД2`; `Наименование ОКПД2` хранится служебно и не выводится отдельной колонкой.
- Модальное окно ОКПД2 имеет кнопку `Закрыть` в footer по паттерну модалки ТН ВЭД.
- При смене ТН ВЭД выбранный ОКПД2 очищается, если код ТН ВЭД изменился, а код категории пересчитывается по ТН ВЭД.
- При смене `Вид товара` frontend очищает `ТН ВЭД`, `ОКПД2` и код категории, затем пользователь выбирает доступный ТН ВЭД заново.
- Backend-валидатор проверяет, что `Вид товара` разрешает выбранный ТН ВЭД, код категории соответствует ТН ВЭД, а код и наименование ОКПД2 соответствуют выбранному ТН ВЭД; наименование при сохранении берётся из маппинга.
- Полное наименование формируется по паттерну косметики:
  `Вид товара + товарный знак + доп. наименование`.
- Если товарный знак `без товарного знака`, доп. наименование обязательно.
- Товарный знак заполняется по паттерну косметики, включая переключатель пустого/без товарного знака.
- Каноническое значение отсутствующего товарного знака для toys: `без товарного знака` в нижнем регистре.
- Таблица позиций и предпросмотр скрывают `без товарного знака` из полного имени регистронезависимо, чтобы старые записи `БЕЗ ТОВАРНОГО ЗНАКА` тоже отображались корректно.
- Модель/артикул производителя разбит на:
  - тип: `Модель`, `Артикул`, `Модель / Артикул`;
  - текстовое значение модели/артикула.
- Поле модели/артикула не заполняется автоматически при открытии формы.
- Для отсутствующей модели/артикула добавлен переключатель по паттерну обуви/артикула: при включении на backend уходит `отсутствует`.
- Backend дополнительно приводит пустую модель/артикул к `отсутствует`, чтобы в позицию не сохранялась пустая строка.
- `Полностью заменить сведения атрибута Модель / артикул производителя` не вводится пользователем и не хранится в модели `Toys`; в итоговом просмотре/предпросмотре/экспорте всегда отдаётся `нет` в нижнем регистре.
- `Вид товара` — выпадающий список из справочника.
- `Материал изделия` — выпадающий список из справочника.
- `Минимальный возраст ребенка` — выпадающий список из справочника.
- `Вид товара (при отсутствии в справочнике)` пока не трогаем.
- `Состав` — свободное поле с нормализацией латинской раскладки в кириллицу по паттерну косметики.
- На поле `Состав` стоит такая же tooltip-пометка с красной иконкой, как в косметике: можно вводить кириллицу, цифры и знаки препинания; латинская раскладка конвертируется в русскую, остаточная латиница удаляется на frontend и дополнительно запрещена backend-валидатором.
- `Ед. срока службы` больше не выбирается пользователем в UI: форма передает скрытое значение `мес`, backend при сохранении/копировании принудительно пишет `мес`, предпросмотр и Excel-выгрузка тоже выводят месяцы.
- В строке периода использования toys стоят четыре поля по паттерну косметики: `Хар-ка срока исп-ния`, `Срок годности, мес.`, `Период годности: дата от`, `Период годности: дата до`.
- `Период годности: дата от` и `Период годности: дата до` добавлены по паттерну косметики.
- `Дата до` на frontend и backend должна быть не раньше чем через месяц от текущей даты.
- Если переключатель РД выключен, список стран ограничен `ГОНКОНГ`, `РОССИЯ`, `КИТАЙ`.
- Если переключатель РД включен, список стран раскрывается до общего справочника стран.
- `GTIN`, `Статус карточки товара в Каталоге`, `Результат обработки данных в Каталоге` пока не собираются в форме и не заполняются в экспорте.

## Связанные изменения вне `toys`

- В `save_cosmetics` товарный знак также сохраняется через `normalize_trademark_placeholder(...)`.
- Для косметики это нормальное поведение: placeholder `БЕЗ ТОВАРНОГО ЗНАКА` приводится к каноническому `без товарного знака`.
- Текст backend-валидации косметики по обязательному доп. наименованию тоже использует `без товарного знака`.
- Шаблоны и JS косметики не переводились на новую механику toys; их отдельная логика остаётся своей.

## Правило ведения

При следующих изменениях `toys` обновлять этот файл:

- какие подкатегории добавлены;
- какие Excel-источники использованы;
- какие slug и category codes заведены;
- какие поля формы отличаются от базового flow;
- какие ограничения по ТН ВЭД и номинальным/количественным полям согласованы.
- Миграции переносить только после сверки MRS-chain: `down_revision` должен соответствовать текущей MRS-цепочке.
