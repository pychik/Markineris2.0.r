# Интеграция Markineris → Тезаурус

## Подбор РД и выбор компании-обработчика

Документ для разработчиков Markineris: что вызывать, в каком порядке и что делать
с ответом. Полный справочник по всем ручкам Тезауруса — в `tezaurus-api.md`.

---

## Что появилось

Две ручки, обе на существующей интеграции — новых механизмов авторизации не нужно.

| Ручка | Зачем | Меняет состояние |
|---|---|---|
| `POST /api/v1/rd/match` | Подобрать РД на все позиции заказа | нет |
| `GET \| POST /api/v1/processing-companies/select` | Выбрать компанию-обработчика | **да** |

Разница в последнем столбце принципиальна, к ней вернёмся.

---

## Подключение

```
Базовый адрес:  TEZAURUS_BASE_URL
Авторизация:    Authorization: Bearer <TEZAURUS_API_TOKEN>
Content-Type:   application/json; charset=utf-8
Таймаут:        30 секунд хватает с запасом, см. «Производительность»
```

Токен тот же, что для синхронизации словарей.

---

## Порядок вызовов

На один заказ приходится **один вызов подбора РД** и **один вызов выбора компании**.
Не по позиции, не в цикле.

```
                    заказ готов к обработке
                              │
                              ▼
              ┌───────────────────────────────┐
              │  POST /api/v1/rd/match        │   один вызов,
              │  все позиции разом            │   безопасно повторять
              └───────────────┬───────────────┘
                              │
                     has_problem == true ?
                    ┌─────────┴─────────┐
                   да                  нет
                    │                   │
                    ▼                   ▼
         заказ в проблему      ┌─────────────────────────────┐
         оператору,            │  GET /processing-companies  │  один вызов,
         компанию не           │  /select                    │  повторять нельзя
         запрашиваем           └──────────────┬──────────────┘
                                              │
                                              ▼
                                     заказ уходит в работу
```

Ключевое: **если РД подобрались не на все позиции, компанию не запрашивайте**.
Заказ всё равно идёт к оператору, а лишний вызов впустую сдвинет очередь раздачи.

## Шаг 1. Подбор РД

### `POST /api/v1/rd/match`

Присылайте заказ целиком. Позиции, где РД уже указал клиент, включать не нужно.

```json
{
  "order_id": 52117,
  "category": "одежда",
  "positions": [
    {
      "position_id": 918273,
      "product_type": "ПЛАТЬЕ",
      "tnved_code": "6204420009",
      "tnved_prefix": "6204",
      "country": "КИТАЙ",
      "is_children": false,
      "gender": "Жен.",
      "content": "хлопок 95%, эластан 5%",
      "materials": null
    },
    {
      "position_id": 918274,
      "product_type": "ТУФЛИ",
      "tnved_code": "6403590000",
      "tnved_prefix": "6403",
      "country": "РОССИЯ",
      "is_children": false,
      "materials": {"top": "натуральная кожа", "lining": "текстиль", "bottom": "полиуретан"}
    }
  ]
}
```

Обязательны только `position_id`, `product_type`, `tnved_prefix` и `country`.
Остальное принимается и не мешает.

**`country` берите из нашего же справочника** — `GET /api/v1/export/countries`,
ветка `user_rd`. Сравнение идёт по точному совпадению, поэтому «КНР» вместо
«КИТАЙ» даст отказ на ровном месте. Свободный ввод в это поле пускать нельзя.

**Дедупликацию не делайте.** Позиции с одинаковыми критериями считаются
у нас один раз, присылайте всё как есть.

**Лимит — 1000 позиций** в одном запросе. Больше — `413`.

### Ответ

```json
{
  "status": "ok",
  "order_id": 52117,
  "has_problem": true,
  "positions_total": 2,
  "positions_found": 1,
  "positions_not_found": 1,
  "results": [
    {
      "position_id": 918273,
      "found": true,
      "rd": {
        "rd_type": "Декларация соответствия",
        "rd_name": "ЕАЭС N RU Д-CN.РА02.В.23226/26",
        "rd_date": "2026-03-03",
        "rd_date_to": "2031-03-01"
      }
    },
    {
      "position_id": 918274,
      "found": false,
      "reason": "Нет действующего РД с ТН ВЭД 6403"
    }
  ]
}
```

На каждую позицию ровно один результат. Порядок совпадает с запросом,
но раскладывайте по `position_id`, не по индексу.

`rd_type` — строго `Декларация соответствия` или `Сертификат`, других значений
не будет. `rd_name` не длиннее 100 символов. Даты в `YYYY-MM-DD`.

### Что делать с результатом

```
has_problem == false  →  все позиции укомплектованы, заказ можно отправлять
has_problem == true   →  заказ в проблему, оператору
```

При `has_problem: true` **всё равно записывайте найденные РД в позиции**.
Оператор разберётся только с теми, где `found: false`, вместо того чтобы искать
документы заново на весь заказ.

Текст `reason` человекочитаемый, его можно показывать оператору как есть:

- `Нет действующего РД с ТН ВЭД 6403` — под этот код у нас нет живых документов
- `Нет действующего РД с ТН ВЭД 6204 на страну ТУРЦИЯ` — код есть, страна не совпала
- `Нет РД под тип товара «ГАЛСТУК» (ТН ВЭД 6215, КИТАЙ)` — не нашлось под этот тип
- `В позиции не указан код ТН ВЭД` — позиция пришла без ТН ВЭД

### Повторные вызовы

Ручка ничего не меняет на нашей стороне. Таймаут, разрыв, `5xx` — повторяйте
спокойно, сколько нужно.

## Шаг 2. Компания-обработчик

### `GET | POST /api/v1/processing-companies/select`

> ### Эта ручка меняет состояние
>
> Компании выдаются по кругу: каждый вызов отдаёт следующую и сдвигает очередь.
> Так нагрузка расходится равномерно, а не оседает на первой подходящей.
>
> Отсюда три правила:
>
> - **вызывайте только когда компания действительно нужна заказу** — не для
>   предпросмотра, не для проверки доступности;
> - **не ставьте в цикл повторов.** Если ответ не дошёл, повтор возьмёт
>   следующую компанию, а не ту же самую. Ничего не сломается, но раздача
>   перекосится;
> - **чтобы просто посмотреть список**, есть `GET /api/v1/export/processing-companies` —
>   она ничего не меняет и дёргать её можно свободно.

Параметры принимаются и в query, и в JSON-теле:

```
GET /api/v1/processing-companies/select?category=обувь&origin=импорт
```

```json
POST /api/v1/processing-companies/select
{"category": "обувь", "origin": "импорт"}
```

| Параметр | Обязательный | Значения |
|---|---|---|
| `category` | да | см. таблицу ниже |
| `origin` | да | `рф`, `rf`, `ru`, `russia`, `россия` / `импорт`, `import`, `imported` |
| `is_import` | нет | Вместо `origin`: `1`/`true`/`yes`/`on` — импорт, `0`/`false`/`no`/`off` — РФ |

Категория нормализуется, регистр и `ё` не важны:

| Присылаете | Превращается в |
|---|---|
| `одежда`, `clothes`, `белье`, `нижнее белье`, `underwear`, `linen`, `носки`, `носки и прочее`, `socks`, `hosiery` | `clothes` |
| `обувь`, `shoes` | `shoes` |
| `духи`, `парфюм`, `perfume`, `parfum` | `parfum` |
| `косметика`, `cosmetics`, `beauty` | `cosmetics` |
| `игрушки`, `игрушка`, `toys`, `toy` | `toys` |
| `товары для дома`, `хозтовары`, `хоз товары`, `home goods`, `home_goods`, `household` | `home_goods` |

Обратите внимание: **бельё и носки относятся к `clothes`**, отдельных компаний
под них нет.

### Ответ

```json
{
  "ok": true,
  "matched": true,
  "criteria": {"category": "shoes", "origin": "import"},
  "company": {
    "title": "Аврора",
    "inn": "4400023120",
    "is_active": true,
    "sort_order": 5,
    "allowed_categories": ["clothes", "shoes", "parfum"],
    "allowed_origins": ["rf", "import"]
  },
  "selection": {
    "mode": "shuffle_queue",
    "cycle_no": 1,
    "cycle_position": 1,
    "cycle_size": 8,
    "queue_rebuilt": true
  }
}
```

Для работы нужны `company.title` и `company.inn`. Блок `selection` —
диагностический, показывает положение в текущем круге; в бизнес-логике
он не нужен, но его удобно писать в лог, если раздача покажется неравномерной.

### Когда компании нет

```json
HTTP 409
{
  "ok": false,
  "matched": false,
  "message": "Для категории и происхождения не настроена включенная компания-обработчик.",
  "criteria": {"category": "toys", "origin": "import"},
  "company": null
}
```

`409` означает, что запрос корректен, но настройки компаний не покрывают эту пару.
Повторять бесполезно — это повод написать нам, а не ретраить.

## Разбор ошибок

Во всех ответах есть булев `ok`. Проверяйте сначала его, потом HTTP-код.

```
200 + ok:true    → всё хорошо
400              → запрос не прошёл валидацию, повторять без изменений бесполезно
401              → токен отсутствует или неверен
409              → запрос корректен, но подходящей записи нет
413              → больше 1000 позиций
5xx              → наша проблема, повторяйте с задержкой
```

Текст ошибки лежит в поле `error` либо `message` — **сейчас две ручки отдают
его по-разному**. Чтобы не писать две ветки, читайте так:

```python
text = payload.get("error") or payload.get("message") or "неизвестная ошибка"
```

У `/rd/match` дополнительно есть машиночитаемый `code`:

| `code` | HTTP | Когда |
|---|---|---|
| `invalid_body` | 400 | тело не JSON или не объект |
| `invalid_positions` | 400 | `positions` не массив, пуст, или у позиции нет `position_id` |
| `too_many_positions` | 413 | больше 1000 позиций |

## Пример клиента

```python
import requests


class TezaurusClient:
    def __init__(self, base_url: str, token: str, timeout: float = 30.0):
        self._base_url = base_url.rstrip("/")
        self._timeout = timeout
        self._session = requests.Session()
        self._session.headers["Authorization"] = f"Bearer {token}"

    def _call(self, method: str, path: str, **kwargs) -> dict:
        response = self._session.request(
            method, f"{self._base_url}{path}", timeout=self._timeout, **kwargs
        )
        try:
            payload = response.json()
        except ValueError:
            # 502/504 от прокси приходят HTML-страницей, а не JSON
            raise TezaurusError(
                f"Ответ не JSON (HTTP {response.status_code})", response.status_code
            ) from None
        if not payload.get("ok", True) and response.status_code >= 400:
            text = payload.get("error") or payload.get("message") or "неизвестная ошибка"
            raise TezaurusError(text, response.status_code, payload.get("code"))
        return payload

    def match_rd(self, order_id: int, positions: list[dict]) -> dict:
        """Безопасно повторять."""
        return self._call(
            "POST", "/api/v1/rd/match",
            json={"order_id": order_id, "positions": positions},
        )

    def take_processing_company(self, category: str, origin: str) -> dict:
        """Сдвигает очередь раздачи. Вызывать один раз на заказ, не в ретрае."""
        return self._call(
            "POST", "/api/v1/processing-companies/select",
            json={"category": category, "origin": origin},
        )


class TezaurusError(Exception):
    def __init__(self, message, status, code=None):
        super().__init__(message)
        self.status = status
        self.code = code
```

Использование в фоновой задаче:

```python
matched = client.match_rd(order.id, [build_position(p) for p in order.positions])

by_id = {r["position_id"]: r for r in matched["results"]}
for position in order.positions:
    result = by_id.get(position.id)
    if result and result["found"]:
        position.apply_rd(result["rd"])
    elif result:
        position.rd_problem = result["reason"]

if matched["has_problem"]:
    order.mark_problem(
        f"РД не подобраны: {matched['positions_not_found']} из {matched['positions_total']}"
    )
    return

company = client.take_processing_company(order.category, order.origin)["company"]
order.set_processing_company(company["title"], company["inn"])
order.send_to_processing()
```

## Производительность

Заказ на 500 позиций подбирается за ~30 мс. Пул документов берётся одним запросом
к базе, дальше всё считается в памяти, повторяющиеся критерии не пересчитываются.
В таймаут 30 секунд укладываемся с запасом в три порядка — разбивать заказ
на части не нужно.

Выбор компании — одна запись в базу, единицы миллисекунд.

---

## Чего подбор пока не умеет

Это влияет на долю отказов, поэтому лучше знать до запуска, а не удивляться
проценту проблемных заказов.

**Наполнение справочника.** Плотно закрыта одежда и текстиль. По обуви документов
почти нет, по парфюмерии и косметике — нет совсем. На такие позиции придёт
`found: false` независимо от качества запроса. Наполнение идёт параллельно.

**Пол не учитывается.** `gender` принимается, но в подборе не участвует —
в описаниях наших документов пол почти не указан, учитывать его не на чем.

**Возраст не учитывается.** `is_children` принимается, но не фильтрует по той же
причине. Документ без указания возраста считается подходящим для любого.

**Материал влияет только на выбор.** При нескольких подходящих документах
предпочтение отдаётся тому, где совпал материал или состав, но сам по себе
материал позицию не отсекает.

**Категория заказа не участвует в подборе.** `category` принимается для
совместимости, отбор идёт по коду ТН ВЭД.

Мы отдаём только документы, подтверждённые в реестре ФСА, с заполненными датами
и запасом не меньше 14 дней до окончания действия. Чужие декларации с портала
ФСА не ищем — это остаётся за вашими операторами.

## Чек-лист перед запуском

- [ ] `country` берётся из `GET /api/v1/export/countries` → `user_rd`, свободный ввод исключён
- [ ] `/rd/match` вызывается один раз на заказ, все позиции разом
- [ ] Найденные РД записываются в позиции даже при `has_problem: true`
- [ ] При `has_problem: true` заказ помечается проблемным, компания не запрашивается
- [ ] `/processing-companies/select` вызывается один раз на заказ и не стоит в цикле повторов
- [ ] Ошибки читаются как `error or message`
- [ ] `409` от выбора компании не ретраится, а эскалируется
- [ ] Заказы больше 1000 позиций разбиваются на части
