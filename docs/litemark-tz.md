# Техническое задание

## Интеграция LiteMark ↔ Markineris: автоматизированная обработка заказов маркировки

---

## 1. О чём это

Markineris принимает от клиентов заказы на маркировку товаров. Сейчас каждый такой заказ вручную
разбирает оператор. Задача интеграции — передать этот процесс на сторону LiteMark и сделать его
автоматическим: Markineris готовит и отдаёт заказ, LiteMark проводит его через полный цикл
(карточки в Национальном каталоге → заказ кодов маркировки → ввод в оборот → УПД) и возвращает готовый результат.

Оператор Markineris остаётся в схеме только как «аварийный выход»: он подключается тогда,
когда автоматическая обработка по какой-то причине не прошла.

**Кто кому звонит.** Markineris выступает сервером и ничего никуда не отправляет по своей
инициативе. Все обращения инициирует LiteMark: вы сами приходите за новыми заказами, сами
сообщаете о ходе работы и сами отдаёте результат.


## 3. Что вы получаете от Markineris до начала работ

| Что | Зачем |
|---|---|
| `base_url` | Базовый адрес API, например `https://stand.markineris.com/api/webhook`. Отдельный для dev-стенда и для production. |
| `key_id` | Публичный идентификатор вашей интеграции. Уходит в заголовке каждого запроса. |
| `shared_secret` | Секрет для подписи запросов. Создаёт и выдаёт Markineris — самостоятельно генерировать не нужно. |
| `minio_endpoint` | Адрес объектного хранилища, куда вы кладёте результат. Только корень S3-endpoint, без пути. |
| `access_key` / `secret_key` | Учётные данные ограниченного пользователя хранилища. **Это отдельная пара, не связанная с `key_id`/`shared_secret`.** |
| `bucket` | Имя бакета для результатов. Приходит также в каждом заказе. |

Что нужно от вас:

- **список внешних IP-адресов**, с которых пойдут запросы (для allowlist). Если адреса
  динамические — сообщите заранее, это надо решать отдельно;

Для dev-стенда и production выдаются **разные** credentials и разные адреса MinIO. Не смешивайте их.

## 4. Аутентификация и подпись

Каждый запрос подписывается. Запрос без подписи или с неверной подписью отклоняется.

### 4.1. Обязательные заголовки

| Заголовок | Что кладём |
|---|---|
| `X-Integration-Key-Id` | Ваш `key_id` |
| `X-Integration-Timestamp` | Текущее время, Unix timestamp в **секундах**, UTC |
| `X-Integration-Nonce` | Уникальная случайная строка, **своя для каждого запроса** |
| `X-Integration-Signature` | Подпись, см. ниже |
| `Content-Type: application/json` | Для всех POST-запросов |

### 4.2. Алгоритм подписи

Подпись — это **обычный SHA-256** от строки, склеенной из трёх частей через символ перевода
строки `\n`:

```
sha256( shared_secret + "\n" + timestamp + "\n" + nonce )
```

Результат переводится в **шестнадцатеричный вид в нижнем регистре** (64 символа) и кладётся
в заголовок `X-Integration-Signature`.

Никакого HMAC, никаких дополнительных полей. Метод, путь и тело запроса в подпись не входят —
одна и та же формула работает для всех шести ручек.

Важные детали:

- разделитель — именно символ с кодом 10 (`LF`, `\n`), **не** `\r\n` и не пробел;
- `timestamp` подписывается как строка, ровно в том виде, в котором уходит в заголовок;
- строка кодируется в **UTF-8** перед хешированием;
- `nonce` нельзя использовать повторно — каждый новый запрос требует нового значения;
  подойдёт GUID/UUID.

### 4.3. Тестовые векторы

Проверьте свою реализацию на этих значениях до того, как отправлять реальные запросы.

**Вектор 1**

```
shared_secret = ls_9f3c1a7e42b8d05c6e1f2a3b4c5d6e7f
timestamp     = 1755500000
nonce         = 0d8b4d7d-0e78-4d4b-b7f1-51d4f2bb2a41
```

Подписываемая строка (три части, два перевода строки):

```
ls_9f3c1a7e42b8d05c6e1f2a3b4c5d6e7f
1755500000
0d8b4d7d-0e78-4d4b-b7f1-51d4f2bb2a41
```

Ожидаемая подпись:

```
41b87d6dd356c87add8c65efee788660f6a422f1bd041337829a3b1e3e9b8ae2
```

**Вектор 2**

```
shared_secret = test-secret
timestamp     = 1700000000
nonce         = 11111111-2222-3333-4444-555555555555
```

Ожидаемая подпись:

```
e6ab6310ff1bb6996c458c9c6448b803dcf79977bfd9511edea5f0dacfc48af1
```

Если ваши значения совпали с обоими — подпись реализована верно.

### 4.4. Ограничения по времени и повторам

- **Окно `timestamp` — 5 минут** в обе стороны от серверного времени. Запрос со временем за
  пределами окна отклоняется с кодом `expired_timestamp`. Синхронизируйте часы сервера по NTP.
- **`nonce` запоминается на 10 минут.** Повторное использование того же значения даёт
  `replay_nonce` (HTTP 409). Это не повод для retry «как есть» — сгенерируйте новый `nonce`,
  новый `timestamp`, пересчитайте подпись.

### 4.5. Хранение секрета

- не хранить `shared_secret` в исходном коде и в конфигурационных файлах, попадающих в репозиторий;
- не передавать его в теле запроса и не писать в логи целиком;
- предусмотреть возможность быстрой замены секрета без пересборки.

## 5. Справочник endpoint-ов

Все пути указаны относительно `base_url`.

| № | Метод | Путь | Назначение |
|---|---|---|---|
| 1 | `GET` | `/orders` | Забрать пачку новых заказов |
| 2 | `POST` | `/orders/accept` | Подтвердить, что заказы приняты в работу |
| 3 | `POST` | `/orders/{order_id}/status` | Сообщить промежуточный статус |
| 4 | `POST` | `/orders/{order_id}/result` | Отдать финальный результат |
| 5 | `GET` | `/orders/problems` | Забрать заказы, снятые с вас по таймауту |
| 6 | `POST` | `/orders/{order_id}/problem-ack` | Подтвердить, что сняли заказ с обработки |

### Формат ответов

Успех:

```json
{
  "status": "ok",
  "message": "...",
  "data": {}
}
```

Ошибка:

```json
{
  "status": "error",
  "message": "Понятное описание проблемы",
  "code": "machine_readable_code"
}
```

Ориентируйтесь и на HTTP-код, и на поле `code` — `message` может меняться, `code` стабилен.

## 6. Шаг 1. Получение заказов

```http
GET {base_url}/orders
```

Заголовки — стандартные четыре из раздела 4. Тела нет.

### Что приходит в ответе

```json
{
  "status": "ok",
  "message": "Orders claimed successfully",
  "data": {
    "orders": [
      {
        "id": 123,
        "dispatch_token": "d6b6c8d262d24cf4808699b1f5c7d1b7",
        "source_file": {
          "file_name": "order_123_source.zip",
          "content_type": "application/zip",
          "size_bytes": 34812,
          "content_base64": "UEsDBBQAAAAI..."
        },
        "upload": {
          "bucket": "litemark-results",
          "object_key": "incoming/123/d6b6c8d262d24cf4808699b1f5c7d1b7/result.zip"
        },
        "processing_company": {
          "title": "ООО Ромашка",
          "inn": "7701234567"
        }
      }
    ]
  }
}
```

### Разбор полей

**`id`** — номер заказа в Markineris. Используется в путях остальных ручек.

**`dispatch_token`** — идентификатор конкретной выдачи заказа именно вам. Сохраните его: он
обязателен в `accept`, `status`, `result` и `problem-ack`. Запрос с чужим или устаревшим токеном
будет отклонён. При повторной выдаче того же заказа токен будет **другим** — всегда используйте
последний полученный.

**`source_file.content_base64`** — исходный zip-архив с заказом, закодированный в base64.
Раскодируйте, сохраните, распакуйте. Внутри — Excel-таблица заказа: это тот самый файл, который
вы загружаете в LiteMark кнопкой «Из файла».

**`upload.bucket` и `upload.object_key`** — куда положить результат. Путь уже сформирован
Markineris. **Менять его нельзя** — ни имя бакета, ни ключ объекта. Свой путь придумывать не нужно.

**`processing_company`** — компания, от имени которой проводится заказ. Содержит `title` и `inn`.

Заказ должен быть проведён именно от этой компании, и **УПД должен быть выставлен от неё же** —
иначе документы разъедутся с тем юрлицом, под которым шла модерация. Компанию выбирает Markineris
и закрепляет за заказом: при повторной выдаче того же заказа она не меняется.

> **Компания приходит в двух местах.** Помимо этого поля она продублирована строкой
> **«Компания обработки»** в служебном листе Excel — рядом с ИНН клиента, ЭДО и типом этикетки.
> Значения всегда совпадают, источник у них один.
>
> **Источником истины считайте `processing_company` из JSON.** Строка в Excel добавлена для
> удобства: она едет вместе с документом, который вы загружаете в LiteMark, и её не нужно
> протаскивать из polling-клиента вручную. Пользуйтесь тем, что удобнее вашему процессу.

> Не путайте `processing_company.inn` с ИНН клиента-заказчика. ИНН клиента, на которого перейдут
> коды маркировки, лежит **внутри Excel** на отдельном листе — см. раздел 8, шаг 7.

### Служебные заголовки ответа

```text
X-Orders-Returned: 10
X-Orders-Limit-Applied: 10
X-Orders-Has-More: true
```

- `X-Orders-Returned` — сколько заказов реально отдано;
- `X-Orders-Limit-Applied` — фактический размер пачки. Это источник истины, размер задаёт
  Markineris в настройках вашей интеграции;
- `X-Orders-Has-More` — `true`, если в пуле остались ещё заказы.

Когда пул исчерпан, дополнительно приходит `X-Orders-Remaining: 0`. В остальных случаях этого
заголовка нет: точное число оставшихся заказов Markineris не считает. Стройте логику опроса
на `X-Orders-Has-More`.

### Как опрашивать

- `X-Orders-Has-More: true` → можно сразу делать следующий запрос;
- заказов нет → увеличьте интервал (разумный минимум — раз в 30–60 секунд);
- один и тот же заказ не будет выдан дважды, пока вы его не потеряете по таймауту (раздел 10).

## 7. Шаг 2. Подтверждение получения

```http
POST {base_url}/orders/accept
```

Отправляется **после** того, как вы действительно приняли заказ: получили ответ, сохранили
`dispatch_token`, раскодировали и сохранили исходный файл, поставили заказ в свою очередь.

Не подтверждайте заказ, который фактически не взяли в работу.

### Тело запроса

Ручка пакетная — подтверждайте всю пачку одним запросом.

```json
{
  "orders": [
    {
      "order_id": 123,
      "dispatch_token": "d6b6c8d262d24cf4808699b1f5c7d1b7",
      "status": "accepted",
      "message": "Заказ принят в обработку"
    }
  ]
}
```

Обязательны `order_id`, `dispatch_token` и `status` со значением ровно `accepted`.
`message` необязателен, но сильно помогает при разборе спорных ситуаций.

### Ответ

```json
{
  "status": "ok",
  "message": "Orders accepted successfully",
  "data": {
    "accepted": [123],
    "rejected": []
  }
}
```

Ответ всегда HTTP 200, даже если часть заказов не принята. **Разбирайте `rejected`** — там будет
`order_id` и причина. Заказ, попавший в `rejected`, у вас в работе не числится.

Повторный `accept` того же заказа ошибкой не считается и ничего не ломает.

### Если `accept` не отправился

Первый корректный `POST /orders/{id}/status` тоже зафиксирует заказ как подтверждённый. Но это
запасной механизм, а не замена: `accept` остаётся основным шагом.

## 8. Регламент обработки заказа

Что нужно сделать с заказом внутри LiteMark, от загрузки файла до готового результата.

Работа ведётся под нужной организацией, начиная с раздела **«Описание продукции»**.

### Шаг 1. Загрузка заказа

Кнопкой «Из файла» («Создать из файла») загрузить Excel из полученного архива.

### Шаг 2. Карточки товаров

1. По кнопке действия получить **GTIN** для всех товаров.
2. По кнопке действия зарегистрировать карточки в **Национальном каталоге**.
3. Дождаться прохождения модерации в «Честном ЗНАКе» — статус товаров изменится
   на **«Ожидает подписания»**.
4. В том же документе описания карточек по кнопке действия **подписать карточки**.

### Шаг 3. Задание на маркировку

Когда карточки перейдут в статус **«Опубликовано»**, кнопкой «Создать заказ» создать задание
на маркировку.

### Шаг 4. Заказ кодов маркировки

В задании перейти в раздел «Заказ кодов маркировки» и создать заказы марок, выбрав способ выпуска
по стране производства товара:

- товар произведён в РФ → **«Производство в РФ»**;
- товар из другой страны → **«Ввезен в РФ (Импорт)»**.

Страна по каждой позиции есть в Excel-таблице заказа.

### Шаг 5. Отправка и получение документов

1. Сформировавшиеся документы отправить кнопкой «Отправить выделенные».
2. Дождаться статуса **«Активный»** и получить выделенные документы.

### Шаг 6. Формирование архива для клиента

Сформировать архив файлов с кодами маркировки **в макете и размере этикетки, указанных в заказе**.
Эти параметры приходят в Excel — см. врезку ниже.

### Шаг 7. Ввод кодов в оборот

1. В задании на маркировку перейти в раздел «Уведомления об операциях» и создать документ
   по типу эмиссии.
2. LiteMark автоматически создаст документ ввода в оборот. Тип зависит от страны производства:
   для импорта — **«Трансграничная торговля»**.
3. Перейти в созданный документ и отправить его. Примерно через минуту проверить статус —
   должен стать **«Обработан»**.

Для товаров, произведённых в РФ, аналогично создаётся документ **«Ввод в оборот»**, где
в соответствующем поле указывается **ИНН клиента**, на которого переходят коды маркировки.

### Шаг 8. УПД

На основании документа уведомления об операциях создать **УПД**:

1. в графе «Получатель» указать ИНН получателя;
2. в реквизитах указать номер УПД;
3. кнопкой «Действие» отправить подписанный документ.

После отправки статус документа меняется на **«Отправлен»**. Номер УПД возвращается в Markineris
вместе с финальным результатом (раздел 9).

> **Где взять реквизиты заказа.** ИНН клиента, наименование и тип организации, оператор ЭДО,
> тип маркировки (макет этикетки) и **компания обработки** лежат в Excel-файле заказа
> на отдельном служебном листе. ТН ВЭД, товарный знак, страна и разрешительная документация —
> в строках позиций.
>
> Отдельных полей в JSON для этого нет, кроме компании обработки: она есть и в JSON
> (`processing_company`), и в листе. Остальные реквизиты — только в файле.

> **Про ЭДО.** Для заказов, приходящих через эту интеграцию, оператор ЭДО берётся из поля заказа
> и по умолчанию это **ЭДО Лайт**. Заказы, где клиент просил другого оператора, в автоматическую
> обработку не попадают.

## 9. Шаг 3–5. Статусы, результат, УПД

### 9.1. Промежуточные статусы

```http
POST {base_url}/orders/{order_id}/status
```

```json
{
  "dispatch_token": "d6b6c8d262d24cf4808699b1f5c7d1b7",
  "status": "in_progress",
  "message": "Карточки отправлены на модерацию в Честный ЗНАК"
}
```

Зачем это нужно: Markineris должен видеть, что заказ жив и движется. Оператор видит эти статусы
в карточке заказа — по ним он понимает, надо ли вмешиваться.

Когда отправлять: заказ поставлен в очередь, началась фактическая обработка, пройден заметный
этап (получены GTIN, карточки зарегистрированы, ушли на модерацию, коды заказаны, документы
отправлены), или произошло что-то важное, но итога ещё нет.

Значения `status` — ваши внутренние, произвольные. Рекомендуемый минимум: `queued`, `in_progress`.

**Чего сюда слать нельзя:** финальные статусы `processed`, `failed`, `problem`, `error` — они
будут отклонены. Для итога есть отдельная ручка.

Просьба: пишите в `message` человекочитаемый текст по делу. Его читает оператор, а не машина.

### 9.2. Загрузка результата в MinIO

Результат загружается **напрямую в объектное хранилище по S3 API**, до вызова ручки результата.
Markineris файл через себя не проксирует.

Используйте `access_key`/`secret_key` ограниченного пользователя хранилища, выданные вам отдельно.
Права у этого пользователя — только на загрузку и прочитать: удалить объект нельзя.

- бакет — из `upload.bucket`;
- ключ объекта — из `upload.object_key`, **ровно как пришёл**;
- формат — **zip**, `content_type: application/zip`;
- для больших файлов можно использовать multipart upload.

`minio_endpoint` — это корень S3-endpoint (например `https://s3.example.com`), без пути.
Варианты вида `https://stand.example.com/upload-result` не подойдут.

После загрузки убедитесь, что клиент не вернул ошибку, multipart завершился полностью,
и размер объекта совпал с ожидаемым.

**Пока файл не загружен — ручку результата вызывать нельзя.**

### 9.3. Успешный результат

```http
POST {base_url}/orders/{order_id}/result
```

```json
{
  "dispatch_token": "d6b6c8d262d24cf4808699b1f5c7d1b7",
  "status": "processed",
  "object_key": "incoming/123/d6b6c8d262d24cf4808699b1f5c7d1b7/result.zip",
  "file_name": "order_123_result.zip",
  "content_type": "application/zip",
  "size_bytes": 156744,
  "upd_number": "УПД-2026-000123",
  "message": "Обработка завершена, коды переданы, УПД отправлен"
}
```

Обязательны: `dispatch_token`, `status`, `object_key`, **`upd_number`**.

`object_key` должен совпадать с выданным байт в байт. Markineris проверяет, что объект
действительно лежит в хранилище по этому ключу.

**`upd_number`** — номер универсального передаточного документа, созданного на шаге 8
регламента. Обычная текстовая строка, до 100 символов; устойчивого формата не требуется.

Поле **обязательное** при `status: "processed"`. Если его не передать, заказ не будет закрыт:
Markineris переведёт его в проблему и вернёт `data.status = "problem"`. Номер подставляется
в карточку заказа рядом с компанией, от которой заказ проводился.

Ответ:

```json
{
  "status": "ok",
  "message": "Result accepted",
  "data": { "order_id": 123, "status": "processed" }
}
```

> **Важно про HTTP 200.** Если не передан `upd_number`, `object_key` не совпал с выданным
> или файла нет в хранилище — ответ всё равно придёт с HTTP 200, но в `data.status` будет `problem`,
> а не `processed`. Заказ при этом уйдёт оператору на ручной разбор.
> **Проверяйте `data.status`, а не только HTTP-код.**

### 9.4. Неуспешный результат

Если обработку завершить не удалось — вызывается та же ручка, но с описанием причины:

```json
{
  "dispatch_token": "d6b6c8d262d24cf4808699b1f5c7d1b7",
  "status": "failed",
  "message": "Честный ЗНАК отклонил модерацию карточек: товарный знак не соответствует РД"
}
```

Допустимые значения: `failed`, `problem`, `error`.

Заказ переводится в статус проблемы и попадает к оператору. **`message` — это то, что оператор
увидит первым.** Пишите конкретную причину: не «ошибка обработки», а что именно и на каком шаге
пошло не так. Текст обрезается до 230 символов, поэтому главное — в начале.

Загружать файл в MinIO в этом случае не нужно.

## 10. Таймаут обработки и проблемные заказы

### 10.1. Правило трёх суток

**На обработку заказа даётся не более 3 суток** с момента подтверждения (`accept`).

Срок выбран с запасом на модерацию в «Честном ЗНАКе»: она может идти сутки, а при аврале и дольше.

Если за это время не пришёл финальный результат, Markineris снимает заказ с автоматической
обработки, переводит его в статус проблемы и передаёт оператору. С этого момента заказ считается
вашим больше не являющимся.

### 10.2. Как вы об этом узнаёте

```http
GET {base_url}/orders/problems
```

Ручка отдаёт заказы, снятые с вас по таймауту и ещё не подтверждённые вами.

```json
{
  "status": "ok",
  "data": {
    "orders": [
      {
        "id": 123,
        "dispatch_token": "d6b6c8d262d24cf4808699b1f5c7d1b7",
        "reason": "processing_timeout",
        "message": "Истёк таймаут обработки 3 суток",
        "happened_at": "2026-08-20T11:04:00"
      }
    ]
  }
}
```

Опрашивайте эту ручку регулярно — достаточно раз в несколько минут.

### 10.3. Подтверждение

```http
POST {base_url}/orders/{order_id}/problem-ack
```

```json
{
  "dispatch_token": "d6b6c8d262d24cf4808699b1f5c7d1b7",
  "message": "Заказ снят с обработки, задание остановлено"
}
```

Подтверждение означает: вы получили уведомление, остановили обработку у себя и больше не будете
слать по этому заказу ни статусы, ни результат.

Пока подтверждения нет, заказ продолжает отдаваться в `GET /orders/problems`.

### 10.4. Что делать, если результат почти готов

Заказ, снятый по таймауту, всё ещё принимает финальный результат. Если обработка завершилась
уже после снятия — загрузите файл и отправьте `result` как обычно: Markineris примет его
и закроет заказ, а оператор увидит, что вопрос решился сам.

Но подтверждать снятие через `problem-ack` при этом всё равно нужно — иначе уведомление будет
приходить повторно.

## 11. Лимиты и требования к надёжности

**Rate limit — 50 запросов в минуту на один `key_id`.** Общий на все ваши процессы, а не на поток.
При превышении приходит HTTP 429 с кодом `rate_limited`. Разумная реакция — подождать до конца
текущей минуты, а не повторять сразу.

**Окно `timestamp` — 5 минут**, **память по `nonce` — 10 минут** (раздел 4.4).

**Повторные попытки.** Retry имеет смысл на сетевых сбоях и на HTTP 500. При этом каждый повтор —
это **новый `nonce`, новый `timestamp` и пересчитанная подпись**. Повтор запроса с теми же
заголовками гарантированно получит `replay_nonce`.

**Идемпотентность.** Повторный `accept` и повторный успешный `result` по уже закрытому заказу
безопасны — состояние не испортится.

**Что не нужно делать:** повторять запрос после `invalid_signature`, `unknown_key_id`,
`ip_not_allowed` или `invalid_dispatch_token` — это ошибки конфигурации или логики, сами
они не пройдут.

## 12. Коды ошибок

| HTTP | `code` | Что означает и что делать |
|---|---|---|
| 401 | `missing_headers` | Нет одного из четырёх обязательных заголовков |
| 401 | `invalid_signature` | Подпись не сошлась. Сверьтесь с тестовыми векторами (4.3) |
| 401 | `expired_timestamp` | Время за пределами пятиминутного окна. Проверьте NTP |
| 400 | `invalid_timestamp` | `timestamp` не число |
| 403 | `unknown_key_id` | `key_id` не найден или интеграция отключена |
| 403 | `ip_not_allowed` | Запрос пришёл с адреса вне allowlist |
| 409 | `replay_nonce` | `nonce` уже использовался. Новый `nonce` + новая подпись |
| 429 | `rate_limited` | Превышен лимит 50 запросов в минуту |
| 400 | `invalid_payload` | Тело запроса не соответствует формату |
| 404 | `invalid_dispatch_token` | Токен не тот, устарел, либо заказ в неподходящей стадии |
| 400 | `unsupported_status` | Недопустимое значение `status` для этой ручки |
| 500 | `integration_not_configured` | Проблема конфигурации на стороне Markineris |
| 503 | `integration_temporarily_unavailable` | Временная недоступность. Повторить позже |
| 500 | `claim_failed`, `accept_failed`, `status_update_failed`, `result_update_failed` | Внутренний сбой Markineris. Можно безопасно повторить позже с новым `nonce` |

Наружу отдаются только такие сообщения. Технических подробностей в ответах нет — при разборе
инцидента обращайтесь к контакту Markineris с указанием `order_id`, `dispatch_token` и времени
запроса.

## 13. Чек-лист приёмки

Интеграция считается готовой, когда пройдены все пункты.

**Доступы**

- [ ] получены `base_url`, `key_id`, `shared_secret` для dev и для production;
- [ ] получены `minio_endpoint`, `bucket`, `access_key`, `secret_key`;
- [ ] переданы внешние IP-адреса для allowlist.

**Подпись**

- [ ] реализация совпала с обоими тестовыми векторами из раздела 4.3;
- [ ] `nonce` уникален для каждого запроса, включая повторы;
- [ ] часы сервера синхронизированы по NTP.

**Полный цикл на dev-стенде**

- [ ] `GET /orders` возвращает заказы, подпись проходит;
- [ ] `source_file.content_base64` корректно раскодирован, архив открывается;
- [ ] `POST /orders/accept` принят, заказ не попал в `rejected`;
- [ ] `POST /orders/{id}/status` принят;
- [ ] файл загружен в MinIO по выданным `bucket` и `object_key` без изменений;
- [ ] `POST /orders/{id}/result` принят, в ответе `data.status = "processed"`;
- [ ] в результате передан `upd_number`;
- [ ] проверен сценарий ошибки: `result` со статусом `failed` и понятным `message`;
- [ ] проверен сценарий таймаута: заказ пришёл в `GET /orders/problems`, отправлен `problem-ack`.

**Устойчивость**

- [ ] обработан HTTP 429 — без немедленного повтора;
- [ ] обработан HTTP 409 `replay_nonce` — повтор с новым `nonce`;
- [ ] при недоступности Markineris заказы не теряются и обработка возобновляется.

## 14. Вопросы к команде LiteMark

Вопросы к обсуждению на созвоне. Разделены по темам.

### Подпись и транспорт

1. Подтверждаете ли, что схема `sha256(secret + "\n" + timestamp + "\n" + nonce)` реализуема
   на вашей стороне без сложностей, и тестовые векторы из раздела 4.3 сходятся?
2. IP-адреса, с которых пойдут запросы, — статические? Сколько их и будут ли отличаться
   для dev и production?
3. Устраивает ли лимит 50 запросов в минуту, или при вашем объёме нужен запас?

### Уведомление о проблемных заказах

4. **Ключевой вопрос.** Мы предлагаем pull-схему: вы опрашиваете `GET /orders/problems`
   и подтверждаете через `problem-ack` (раздел 10). Альтернатива — мы сами вызываем ваш
   endpoint (push). Pull нам предпочтительнее: он переиспользует уже готовую подпись и не требует,
   чтобы мы знали вашу сеть и авторизацию. Подходит ли это вам?
5. Если всё-таки push — какой у вас адрес, схема авторизации и формат подтверждения?
6. С какой периодичностью вам удобно опрашивать `orders/problems`?

### Таймаут и сроки

7. Трое суток на обработку — подтверждаете, что срока хватает с учётом модерации
   в «Честном ЗНАКе»?
8. Модерация ЧЗ может идти дольше трёх суток по независящим от вас причинам. Нужен ли механизм
   продления — например, вы шлёте `status` с признаком «ждём ЧЗ», и таймер сдвигается?
9. Что происходит у вас с заданием, если мы сняли заказ по таймауту, а работа уже почти закончена?

### УПД и результат

10. `upd_number` мы ждём в `result`. Нужен ли нам ещё **сам документ** УПД — файлом?
    Если да: он лежит внутри `result.zip` или это отдельный объект в MinIO? В каком формате
    (PDF, XML, оба)?
11. Что именно кладётся в `result.zip` кроме архива с кодами маркировки?
12. Есть ли у номера УПД устойчивый формат, или это произвольная строка? Какая максимальная длина?
13. Может ли на один заказ приходиться более одного УПД (например, при разбиении по странам
    производства)?

### Обработка и ошибки

14. Насколько детально вы можете описывать причину в `message` при `failed`? Нам важно, чтобы
    оператор понимал, что делать, без обращения к вам.
15. Различаете ли вы «ошибка данных заказа» (переделывать клиенту) и «технический сбой»
    (можно повторить)? Готовы ли разводить это по значениям `status` — например,
    `problem` против `error`?
16. Обрабатываете ли вы заказы параллельно? Если да — сколько одновременно, и есть ли ограничение
    со стороны ЧЗ?
17. Что происходит, если обработка прошла успешно, файл загружен, но вызов `result` не прошёл
    (сеть, наша недоступность)? Есть ли у вас очередь повторов и как долго она живёт?
18. Отказ модерации в «Честном ЗНАКе» — насколько частый случай в вашей практике и какие причины
    встречаются чаще всего?
19. Проверяете ли вы данные карточек до отправки в ЧЗ, или об отказе узнаём уже по факту?
    Нам важно понимать, через сколько времени после `accept` может прийти `failed`.

### Организационное

20. Какой размер пачки в `GET /orders` для вас комфортен? По умолчанию 10.
