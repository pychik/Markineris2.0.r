# Markineris2.0.r
Markineris2.0.r for special agents

## Информационные команды

- Команда help, для просмотра доступных команд и их краткое описание
```shell
make help
```

### Авторизация и завершение старых сессий

- Сессии Flask-Login и cookie «Запомнить» привязаны к текущему хешу пароля пользователя: `User.get_id()` формирует подписанный идентификатор, а `setup_login()` сверяет его при загрузке пользователя. После смены пароля прежние сессии и cookie перестают авторизовывать при следующем запросе. Дополнительные запросы к БД и миграция не нужны.
- При первом развёртывании этого механизма все ранее выданные сессии и cookie «Запомнить» станут недействительны; пользователям потребуется войти снова.

### Ежедневные задачи RQ

- Расписание находится в `app/redis_queue/scheduler.py`; время определяется часовым поясом процесса планировщика.
- 00:00 — обработка неоплаченных транзакций.
- 00:05 — перевод отправленных заказов в обработанные.
- 00:10 — отмена старых новых заказов.
- 00:15 — отклонение карточек по дате РД.
- 00:20 — очистка вложений чатов заказов по сроку хранения 14 дней.
- Задачи используют очередь `scheduled`. При одном воркере они выполняются последовательно и могут начаться позже указанного времени. Для применения нового расписания нужно перезапустить планировщик.

### Временный локальный справочник Tezaurus

- При `TEZAURUS_SYNC_ENABLED=0` формы, Excel-загрузка и проверка совместимости при копировании заказа читают runtime-снимок `TEZAURUS_FALLBACK_RUNTIME_DATA_DIR`, а если он недоступен — seed из `app/tezaurus_fallback/data/`. Фирма для карточки выбирается из локального списка с очередью в Redis; опрос Tezaurus отключён.
- При `TEZAURUS_SYNC_ENABLED=1` планировщик обновляет Redis-кэш из Tezaurus, формы читают его, а фирма подбирается через API Tezaurus. Для списков стран при пустом или недоступном кэше сначала используется сохранённый снимок `tezaurus_fallback`, затем старые списки приложения.
- Если внешний Tezaurus недоступен при `TEZAURUS_SYNC_ENABLED=1`, справочники продолжают работать из последнего Redis-кэша, пока Redis жив и наполнен. Ошибки синхронизации не удаляют старый кэш. Рискованное место — назначение обрабатывающей фирмы для карточек: оно обращается к API Tezaurus и при сбое возвращает контролируемую ошибку, не переводя карточки в частично обновлённое состояние.
- Ежедневная задача `export_tezaurus_fallback_snapshot_task` сохраняет последний Redis-снимок в MinIO bucket `static` под `tezaurus_fallback/current/manifest.json` и версионированные JSON-файлы под `tezaurus_fallback/snapshots/<revisions>/`. При старте контейнера снимок восстанавливается из MinIO до запуска gunicorn/worker/scheduler. Расписание задаёт `TEZAURUS_FALLBACK_SNAPSHOT_CRON` (`15 0 * * *` по умолчанию; в этом проекте это время уже занято другой задачей, поэтому на проде можно задать отдельное значение).
- Страна проверяется одинаково при заполнении заказа, создании карточки, загрузке Excel и копировании: с РД используется общий список, без РД — список категории из активного источника (Redis при флаге `1`, локальный снимок при `0` или сбое Redis). Носки используют список одежды. Для косметики и игрушек, если отдельного списка Tezaurus нет, используются страны их подкатегории.
- Значение по умолчанию — `0`. После изменения флага нужно перезапустить приложение, воркеры и планировщик, чтобы все процессы использовали один источник данных.
- Подробности и дата снимка: `app/tezaurus_fallback/README.md`.

### CRM-флаг РФ-заказа
- В CRM карточках обычных заказов значок флага показывает, что все позиции заказа имеют страну `РОССИЯ`.
- Флаг считается в общем SQL-агрегаторе `app/utilities/sql_categories_aggregations.py` и протаскивается через `app/views/crm/helpers.py`; отдельной колонки и миграции в `orders` нет.

### CRM-отчет активности операторов
- Роут отчета: `/crm_uoc/avg_order_processing_time_report`.
- Отчет показывает по каждому оператору количество обработанных заказов, строк, марок и среднее время обработки в минутах и часах.
- Заказ попадает в отчет по факту заполненного `orders.m_finished`; это покрывает обычное завершение обработки и переход проблемного заказа в статус `Проблема решена`.
- Дневные колонки распределяют заказы по длительности `m_finished - m_started`: до 1 дня, до 2 дней, до 3 дней и более 3 дней.
- Максимальный диапазон формирования отчета - 4 месяца. На фронте запрос блокируется через `make_message`, если пользователь выбрал больший период.
- В интерфейсе отчета есть раскрываемая справка по иконке `i`; шаблон описания лежит в `app/templates/crm_mod_v1/reports/avg_order_processing_time/report_description.html`.
- Excel-выгрузка использует те же данные и порядок колонок, что и HTML-таблица.

### Одежда: состав и ТН ВЭД 4203

- ТН ВЭД с префиксом `4203` разрешён только при наличии отдельного материала «Кожа», «Натуральная кожа» или «Композиционная кожа» в составе. Регистр, пробелы и проценты не влияют на проверку. Искусственная кожа, экокожа и замша не подходят под это правило.
- Проверка применяется при добавлении и редактировании позиции обычного заказа, создании и редактировании карточки товара и импорте Excel. При копировании из истории несовместимые позиции пропускаются с предупреждением по существующим правилам копирования.
- При удалении кожи из состава выбранный код `4203…` сразу очищается. Другие префиксы ТН ВЭД и категории работают по прежним правилам; отдельной проверки при отправке черновиков нет.
- Общее правило находится в `app/utilities/clothes_tnved_content.py`; браузер получает то же выражение через JSON и использует `app/static/main_v2/js/categories/clothes_tnved_content.js`. Проверка не обращается к БД или внешним сервисам. На странице проверки РД она не подключается.
- Регрессионные тесты из корня проекта: `python3 -B -m unittest discover -s tests -p 'test_clothes_tnved_content.py' -v`. Для проверки JS нужен Node.js; тест без него пропускается.

### Белье: комплект постельного белья
- Вид товара `КОМПЛЕКТ ПОСТЕЛЬНОГО БЕЛЬЯ` заполняется как одна позиция заказа с дочерними строками состава комплекта.
- Количество марок для КПБ считается по количеству комплектов и хранится в `Linen.kpb_quantity`.
- Дочерние строки состава хранятся в `LinenSetItem` / `linen_set_items` и связаны с `Linen.set_items`.
- В карточках товаров КПБ доступен как один товар с дочерними строками состава; для модерации используется `Linen.is_approved`.
- При создании GTIN-заказа из карточки КПБ копируется состав комплекта, а введенное количество сохраняется в `Linen.kpb_quantity`.
- Через Excel upload КПБ временно запрещен: комплект нужно заполнять через форму в сервисе.
- Миграция для `linen.kpb_quantity`, `linen.is_approved` и `linen_set_items` генерируется локально и не коммитится:
```shell
cd app
flask db migrate -m "add linen set items"
flask db upgrade
```


### Быстрые заказы из карточек: компании обработки и УПД
- Временное отличие: категория `игрушки` отключена в карточках товаров и быстрых GTIN-заказах из карточек.
- Отключение заведено как временный feature flag в `app/views/main/product_cards/constants.py`; чтобы вернуть категорию, нужно убрать игрушки из `PC_DISABLED_CARD_CATEGORIES` и `PC_DISABLED_ORDER_CATEGORIES`.
- Обычная форма заказов категории `игрушки` не отключалась и должна работать в прежнем режиме.
- Архив Excel для быстрых заказов из карточек делится по компаниям обработки через `fast_order_companies`.
- При создании быстрого заказа компании сохраняются в `fast_order_companies`: одна строка на одну уникальную компанию в рамках заказа.
- В товарные позиции быстрого заказа сохраняется только ссылка `fast_order_company_id`.
- В CRM для быстрого заказа модалка УПД показывает отдельное поле УПД для каждой компании из `fast_order_companies`.
- Копирование быстрого заказа из истории переносит только позиции с одобренными данными и заполненной компанией обработки; остальные позиции пропускаются с предупреждением.
- Миграции для этих изменений генерируются локально и не коммитятся:

```shell
cd app
flask db migrate -m "add fast order companies"
flask db upgrade
```
- В сгенерированной миграции должны быть: создание `fast_order_companies`, добавление `fast_order_company_id` в товарные таблицы заказов и изменение `orders.processing_info` на `text`, если оно еще не применено в базе.

### Организация заказа: backend-валидация
- Тип организации должен входить в `settings.COMPANY_TYPES`: `ИП`, `ООО`, `АО`, `ПАО`, `НПАО`, `ГКФХ`, `Филиал`, `Рынок`, `Магазин`, `НАО`; проверка выполняется без учета регистра и сохраняет каноническое значение из списка.
- `company_idn` принимает только цифры: для `ИП`, `ГКФХ`, `Рынок`, `Магазин` ровно `12`, для остальных типов ровно `10`.
- `company_name` обязателен и не должен начинаться с пробела; при сохранении хвостовые пробелы нормализуются.
- Общая проверка лежит в `app/utilities/validators.py` (`validate_and_normalize_company_fields()`).
- Проверка применяется на backend в создании обычного заказа, создании парфюм-заказа, Excel upload, `send_table`, редактировании организации заказа, перед отправкой обычного заказа в обработку, создании быстрого заказа из `product_cards`, а также перед проверкой и отправкой такого черновика в обработку.
- Ошибки не доходят до записи битых данных в `orders`: HTML-формы получают `flash(..., category='error')` и возврат на форму/заказ, а AJAX-точки `product_cards` отвечают JSON-ошибкой `400`.

### Оформление заказа: дубли в архиве
- Проверка похожего заказа в архиве больше не выполняется при оформлении/отправке заказа в обработку.
- Preflight-ручки оформления (`requests_common.cubaa` и `product_cards` `check_before_process`) продолжают проверять баланс, готовность позиций и обязательные поля, но возвращают `status_order=0` и не блокируют оформление из-за дубля в архиве.

### Оформление заказа: предупреждение о балансе
- Если проверка при оформлении обычного заказа или заказа через карточки товаров выявляет недостаток средств либо невозможность оформления через агента, сообщение показывается в мягком красном блоке «Внимание». Содержание ответа проверки не меняется.

### CRM-массовый перенос заказов AT2
- Массовый перенос `NEW -> POOL` в CRM (`/crm_d/all_new_multi_pool`) доступен `superuser`, модератору `m2r_admin` и агенту тип2 (`role = admin`, `is_at2 = true`).
- `superuser` и `m2r_admin` переносят все новые заказы.
- Агент тип2 переносит только свои заказы и заказы своих клиентов (`orders.user_id = current_user.id` или `users.admin_parent_id = current_user.id`).
- Обычный `admin` без `is_at2` получает предупреждение, заказы не переносятся.
- Логика находится в `app/views/crm/helpers_mo.py`.

### Загрузка досок CRM
- `/crm_dashboard/agents`, `/crm_dashboard/managers` и `/crm_product_cards/cards` сначала возвращают шапку и индикатор загрузки. Доски заказов и карточек запрашиваются через те же маршруты с `bck=1`.
- Списки и счётчики категорий формируются только во втором запросе. Общий загрузчик — `app/static/crm_mod/js/initial_board.js`; при ошибке доступна повторная загрузка.
- Доступ агента типа 2 сохраняется на обоих запросах: в CRM заказов `helper_get_agent_orders(user=current_user)` выбирает его заказы и заказы его клиентов, а в CRM карточек `apply_crm_cards_scope()` ограничивает карточки клиентами агента. Декораторы маршрутов для обычной страницы и `bck=1` одинаковы.
- При сохранении УПД обычного и быстрого заказа сразу показывается общий индикатор и блокируется повторное нажатие кнопки до ответа сервера.
- В переключателе поиска CRM карточек подпись «По артикулу (парфюм — по торговому знаку)» оформлена уменьшенным шрифтом.

### CRM-отчет активности операторов
- Роут отчета: `/crm_uoc/avg_order_processing_time_report`.
- На странице общий фильтр периода и оператора, ниже вкладки 4 отчетов:
  - заказы операторов по категориям;
  - взятые заказы по дням и категориям;
  - среднее время обработки заказов;
  - полные метрики заказов в `.txt` с JSON-массивом для анализа ИИ.
- Заказ попадает в отчеты по факту заполненного `orders.m_finished`; отмененные заказы исключаются через `stage != CANCELLED`.
- В MRS категория `носки и прочее` в отчетах по категориям считается в колонку `Одежда`.
- Отчет среднего времени распределяет заказы по длительности `m_finished - m_started`: до 1 дня, до 2 дней, до 3 дней, до 4 дней и более 4 дней.
- Максимальный диапазон формирования обычных отчетов - 4 месяца, дневного отчета - 1 месяц, отчета полных метрик - 1 год. Ограничения применяются на фронте и на backend.
- В интерфейсе каждой вкладки есть раскрываемая справка по иконке `i`; общие стили описаний лежат в `app/templates/crm_mod_v1/reports/avg_order_processing_time/report_description.html`.
- Excel-выгрузки используют те же данные и порядок колонок, что и HTML-таблицы.

### Реестр наших РД
- Модуль `app/rd_registry/` (модель, сервис, роуты), blueprint `rd_registry` с префиксом `/rd_registry`. Подробности в `app/rd_registry/README.md`.
- Реестр пополняется при CRM-сохранении карточки товара с изменённым блоком РД: `h_update_product_card(crm_=True)` вызывает `remember_rd()` в той же транзакции, с категорией карточки, подкатегорией и ТНВЭД позиции. Второй способ - ручное добавление на странице `/rd_registry/`. Создание карточки и правки клиента в реестр не пишутся.
- На CRM-странице редактирования карточки в шапке блока РД есть кнопка «Реестр РД». Модалка сразу показывает РД с ТНВЭД карточки, поиск по номеру от 5 символов идёт по всему реестру. В подсказках только неархивные РД, которые действуют ещё минимум месяц (то же правило, что в `validate_rd_block`).
- Доступ:
  - страница реестра, добавление и правка - `superuser` и `supermanager`, архив - только `superuser`;
  - поиск для модалки `GET /rd_registry/search` открыт ролям CRM-редактирования (`bck_sumausmumu_required`);
  - агент тип2 видит карточки своих клиентов в CRM только на просмотр, без блока РД, и в реестр не пишет;
  - ссылку «Реестр РД» в меню CRM видят `superuser` и `supermanager`.
- `rd_registry` добавлен в `allowed_blueprints` в `manager_forbidden_handler` (`app/settings/handlers.py`), без этого операторов редиректит с поиска.

### Алерты в Telegram

ElastAlert2 живёт в `docker-compose.elk.yml` как отдельный контейнер, поднимается вместе с `make elk-up`. Раз в минуту опрашивает Elasticsearch, при срабатывании правила шлёт в Telegram.

Правила в `elk/elastalert/rules/`:
- `flask_errors.yaml` — 3+ строки ERROR/CRITICAL в логах Flask за 5 минут
- `nginx_5xx.yaml` — 5+ ответов 500/502/503/504 от nginx за 5 минут
- `apm_exceptions.yaml` — любое Python-исключение через APM-агент (то же что Kibana APM → Errors), группировка по culprit, кулдаун 10 минут
- `apm_failed_transactions.yaml` — любая упавшая транзакция, кулдаун 15 минут на endpoint

Переменные окружения которые нужны:
```dotenv
HEALTHCHECK_BOT=...               # токен Telegram-бота
TELEGRAM_ALERTS_GROUP_ID=...      # chat_id канала с алертами
```

### Health check эндпоинт

`GET /app/health` — проверяет `SELECT 1` к PostgreSQL и `PING` к Redis. Возвращает 200 если всё ок, 503 если что-то упало. Во время тех. обслуживания возвращает `200 {"status":"maintenance"}` — так внешний мониторинг не сходит с ума при плановых деплоях.

Закрыт токеном — без заголовка `X-Health-Token` вернёт 403.

## Cache Bust для static

- Версия для `url_for('static', ...)` задается один раз на старте Flask-контейнера в `app.config['STATIC_VERSION']`.
- Далее `@app.url_defaults` автоматически добавляет `?v=<STATIC_VERSION>` ко всем static URL, если `v` не передан вручную.
- На проде это не зависит от локальной папки `static` внутри `flask_app`, поэтому схема работает вместе с MinIO.
- После нового деплоя или рестарта `flask_app` значение `STATIC_VERSION` меняется, и браузер запрашивает новую статику.
- Ручные `?v=...` в шаблонах добавлять не нужно.

### Проверка товарного знака и вида товара
- Товарный знак не может состоять только из выбранного вида товара, любых подряд идущих полных слов этого вида или этих слов с обозначением пола (`жен`, `жен.`, `женский`, `муж`, `мужской`, `детский` и соответствующие формы) до или после слов товара. Для вида `СКАЛЬНЫЕ ТУФЛИ` недопустимы `Туфли муж` и `муж туфли`. Для вида `Летние кожаные туфли` также недопустимы `Летние`, `Кожаные туфли` и `Тули муж` (одна опечатка в отдельном кириллическом слове); `Туфли 1234` и `Туфли Nike` допустимы. Регистр и знаки препинания не влияют на сравнение. Значения `без товарного знака`, `без бренда`, `нет` остаются допустимыми там, где категория позволяет их использовать.
- Общее серверное правило находится в `app/utilities/validators.py` (`trademark_matches_product_type`). Оно вызывается при ручном добавлении или изменении позиции заказа, создании и обновлении карточки товара, включая модерацию, а также перед копированием заказа из архива.
- При Excel-загрузке после разбора строк и до сохранения проверяются все позиции. Недопустимые товарные знаки попадают в файл ошибок с номером строки; заказ не создаётся.
- JS-проверка в `app/static/main_v2/js/trademark_product_type_guard.js` очищает поле и показывает сообщение до отправки формы. Серверная проверка применяется независимо от JS.

### Баланс до и после в транзакциях
- `user_transactions.balance_before` и `balance_after` хранят `users.balance` до и после проведения транзакции. Заполняются только когда транзакция меняет баланс: у ожидающих, отменённых и старых транзакций поля пустые. Ожидающие получают значения в момент перехода в `success`.
- `users.balance` менять только вместе с транзакцией, которая это изменение описывает:
  - ORM: `UserTransaction.change_user_balance(user, delta)`;
  - raw SQL: `balance_change_sql(user_id, delta, tr_id=...)` или `bill_path=...` из `app/models.py`.
  Прямой `UPDATE users SET balance` оставит поля пустыми.
- `balance_change_sql` читает «до» подзапросом под `FOR NO KEY UPDATE`, той же блокировкой, что берёт UPDATE баланса: конкурентные изменения одного пользователя идут по очереди и не ловят deadlock с `FOR KEY SHARE` от INSERT транзакции. «До» не вычисляется как «после» минус delta, потому что delta бывает дробной.
- Где видно: колонки «Баланс до» и «Баланс после» в истории транзакций кабинета, в «транзакциях клиента» админки (у клиентов агента тип2 скрыты, как и сумма) и в «Контроле транзакций пользователей»; строки в окне деталей успешной транзакции (кабинет, стаф, агент). Excel-выгрузка не менялась.

# Экосбор (`eco_sbor`)

Обычные заказы создаются через семь категорий: обувь, одежда (включая подкатегории), носки и прочее, белье, парфюм, косметика (подкатегории) и игрушки (подкатегории). Форма передает позицию через `utilities/support.py` в `utilities/saving_uts.py::common_save_db`. Объединение одинаковых позиций выполняет `utilities/saving_helpers.py::append_or_merge_position`. Копирование заказа из истории идет через `common_save_copy_order`; загрузка Excel использует `utilities/upload_order/*` и шаблоны `app/download_dir/system_files/`.

- `CommonMixin.weight_grams` хранит общий вес одной позиции в граммах как nullable integer. Пустое значение оставлено для ранее созданных позиций. **Файл миграции не создавался:** после переноса изменений выполнить `flask db migrate` и проверить сгенерированную ревизию для семи таблиц позиций (`shoes`, `clothes`, `socks`, `linen`, `parfum`, `cosmetics`, `toys`), затем применить ее штатным способом.
- Во всех формах позиции поле «Общий вес позиции» обязательно, принимает только целое число граммов больше нуля. Подсказка поля содержит текст для отчетности РОСПРИРОДНАДЗОР. Вес показывается в правой итоговой плашке и последним полем модального просмотра позиции; в таблицах позиций колонки веса нет. При объединении одинаковых позиций вес суммируется, старые позиции без веса отдельно от новых. Отправка черновика с позицией без веса блокируется до ее исправления.
- При копировании заказа из истории позиции без веса исключаются с предупреждением. Если подходящих позиций нет, копирование останавливается. При копировании отдельных позиций значение веса переносится в форму редактирования.
- Скачиваемые Excel-шаблоны содержат обязательную колонку «Вес в граммах». Подсказка веса переносится внутри своей ячейки; проверку значения выполняет сервер при загрузке и возвращает ошибку с номером строки. Старая версия шаблона отклоняется с просьбой скачать новую. На странице Excel-загрузки отображается предупреждение об изменении.
- На действующей панели `/admin_control/` кнопка «Отчет экосбор» находится в колонке «Разное» рядом с «Тестированием модулей» и имеет плашку `New`. Она показывается только `superuser` и ведет на `/admin_control/eco-sbor`; прямой доступ к отчету также ограничен `superuser`. Отчет выбирает заказы CRM в статусах `SENT` и `CRM_PROCESSED` по `sent_at` при наличии УПД. Для обычного заказа фирма и УПД берутся из отдельных полей с резервным чтением старого `processing_info`; для заказов на модерации используется фирма позиции и ее УПД. Фильтры: даты, категория, подкатегория, проводящая фирма. В веб-версии постоянная вкладка «Фирмы» показывает количество КМ и вес в тоннах по каждой проводящей фирме с заказами; строки раскрываются для разбивки по категориям. Фирмы и категории отсортированы по убыванию количества КМ. Остальные вкладки группируют строки по категории и подкатегории. Excel содержит лист «Фирмы», включая фирмы с нулевыми итогами, и отдельный лист для каждой группы. Итоговый вес суммируется по позициям с указанным весом, даже если у других позиций вес отсутствует. В веб-отчёте такие итоги отмечены серым бейджем с числом позиций без веса и подсказкой; в Excel число указано в строке итога и на листе «Фирмы». Прочерк вместо веса показывается, только если вес не указан ни у одной позиции. Это правило относится и к заказам из карточек модерации. Каждая строка детального отчета содержит дату, фирму, заказ, категорию, подкатегорию, артикул, вид товара, ТН ВЭД, количество и вес. У старых позиций вес в Excel остается пустой ячейкой.
- Таблица отчета загружается фоновым запросом при открытии страницы по ссылке и после нажатия «Обновить»; при изменении фильтров прежние результаты скрываются до повторного нажатия. Список проводящих фирм загружается вместе с первым отчетом и обновляется отдельно при изменении периода, категории или подкатегории. После загрузки таблица и итоги появляются с тем же эффектом `faded`, что и карточки заказов CRM. Размер страницы берется из `settings.PAGINATION_PER_PAGE` (сейчас 50): выбор страницы происходит в SQL через `LIMIT/OFFSET`. Все отображаемые поля позиции выбираются сразу в SQL, без повторной загрузки позиций через ORM. Счетчики вкладок и список фирм считаются отдельными SQL-запросами без загрузки всех заказов в память; список фирм не пересчитывается при перелистывании и сортировке. Индикатор загрузки соответствует CRM-карточкам, запрос таблицы ограничен ожиданием 60 секунд. Сортировка даты и переходы между вкладками/страницами работают без перезагрузки; пагинатор показывает номера страниц с выделением текущей. Даты в фильтрах отображаются как ДД.ММ.ГГГГ через русский календарь; старые ссылки с ISO-датой также работают. Кнопки «Обновить» и «Скачать отчет» находятся под фильтрами, сверху есть ссылка обратно в панель администратора. Подкатегории отображаются русскими названиями и ограничиваются выбранной категорией; выбор подкатегории из полного списка автоматически выбирает ее категорию. Excel скачивается фоновым запросом за период не более 12 календарных месяцев от начальной даты включительно; сервер проверяет лимит до SQL-запроса. Для выгрузки результат читается пакетами серверным курсором и записывается в потоковый XLSX, чтобы не держать все строки и ячейки в памяти. Вес старых позиций остается пустой ячейкой. Для более длинного периода можно скачать несколько файлов по частям; просмотр веб-отчета этим лимитом не ограничен. Отчет отбирает и датирует позиции только по `orders.sent_at`; заказ без даты отправки в него не входит, даже если заполнен `closed_at` или стоит статус `CRM_PROCESSED`.
- Колонка «Количество марок» соответствует количеству маркируемых единиц в заказе: для обуви, одежды и носков суммируются количества по размерам с учетом коробок; для косметики и игрушек используется количество позиции; для упакованной парфюмерии и белья учитываются упаковки, для комплекта белья — число комплектов. SQL считает итоги количества и веса по всей выбранной вкладке, а не только по открытой странице. Общие итоги по фильтрам показаны над вкладками мягкими бейджами в стиле финансовых отчетов; в Excel итоговая строка есть на каждом листе. Позиции без веса входят в количество марок; заполненный вес других позиций сохраняется в итогах, а число пропусков отмечено бейджем. Это правило действует и для карточек модерации.
- В Excel колонка «Подкатегория» содержит русское название из общего справочника; `common` показывается как «основная одежда». Код подкатегории остается внутренним ключом группировки и фильтров. Колонка ТН ВЭД сохранена.
- В обоих обработчиках смены статуса CRM переход в `CRM_PROCESSED` теперь разрешен только из `SENT` при заполненном `sent_at`; проверка выполняется на сервере и не меняет остальные переходы. Массовый перевод уже отбирает только отправленные заказы.
- При сохранении фирмы и УПД в окне CRM сразу показывается штатный индикатор загрузки; он закрывается после ответа или ошибки. Кнопка сохранения на время запроса отключается, а ошибка выводится в окне и сообщением CRM. Для обычного заказа сохранение не загружает список фирм быстрого заказа; оба сценария формируют ответ из значений, полученных до `commit`, чтобы не перечитывать ORM-объект после записи. Если сохранение длится от 2 секунд, лог `UPD save slow` показывает время загрузки заказа, подготовки и `commit` отдельно.
- Общий `loadingCircle()` на страницах `main/base_v2.html` теперь показывает панель загрузки в стиле CRM; изменены только разметка оверлея и CSS. Вызовы и логика скрытия индикатора в заказах, админке и кабинете не менялись. CRM, CRM карточек, экосбор и экран без CRM уже используют такую панель.
- Для обычных заказов CRM теперь хранит проводящую фирму и УПД в отдельных nullable-полях `orders.processing_company_key`, `orders.processing_company_label`, `orders.upd_number`. При сохранении CRM заполняет их одновременно со старым `processing_info`, чтобы существующие экраны продолжали работать. Модальное окно CRM предварительно выбирает сохраненную фирму и номер УПД; для старых заказов читает однозначную пару из `processing_info`. У заказов на модерации источником остаются `fast_order_companies`. Отчет экосбора сначала использует новые поля обычного заказа, затем старый `processing_info`; для модерации использует только фирму позиции с заполненным УПД. Поля обычного заказа при отборе быстрых позиций не используются.
- **Миграция не создана по договоренности:** сгенерировать ее через `flask db migrate`, проверить три nullable-поля и индекс `processing_company_label`, применить через `flask db upgrade`. После этого в `flask shell` вызвать `from utilities.scripts_manual.backfill_order_processing_info import backfill_order_processing_info`, затем `backfill_order_processing_info()` для предварительного отчета и `backfill_order_processing_info(commit=True)` для переноса. Скрипт идет пакетами, не перезаписывает уже заполненные значения, пропускает неоднозначные и конфликтующие строки и возвращает счетчики с примерами ID для проверки. Повторный запуск безопасен.
- Поле веса показывает пример «Пример 100». Вкладки веб-отчета оформлены как серые кнопки: светлее при наведении и темнее для выбранной вкладки. После «Обновить» первые страницы всех вкладок загружаются одним запросом; переключение вкладок не обращается к серверу. Переход на другую страницу внутри вкладки загружает ее отдельно. Названия фирм с HTML-сущностями (например, `&#34;`) декодируются для отображения; исходное значение сохраняется в фильтре.
